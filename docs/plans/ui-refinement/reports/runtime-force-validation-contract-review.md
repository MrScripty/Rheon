## Execution blockers and prerequisite evidence

1. **Exact test bodies are absent.** Implement the two proposed cases as ignored
   tests in the separately owned desktop test module. Independently inspect every
   constructor, dispatch, recorder/read, filesystem and assertion helper before
   compiling/listing; there must be no broad fixture or fallback execution. The
   exact compiled list must show both names with ignored status. Do not transfer
   the older 197-name binary as the integration executable.
2. **The final source/executable closure is not yet sealed.** Pin the final
   commit/tree and affected-source manifest, test/helper bytes, Cargo.lock,
   toolchain/features and exact executable hash after those bodies exist. Verify
   that the executor's source/binary matches those seals. A backend admission for
   unchanged core does not admit the changed desktop/test closure.
3. **Existing containment has not been demonstrated by this review.** The
   execution owner must identify its already supported wall/CPU/address-space,
   per-file/aggregate-filesystem and captured-output enforcement, and process-group
   termination/survivor checks. Per-file limits or post-run file counting alone
   do not enforce the separate aggregate-root bound. If any required existing
   control is missing, report that exact prerequisite and stop that execution.
   No cgroup/mount provisioning, delegation/permission changes or substitute
   unbounded run is admitted.
4. **Execution remains separately unadmitted.** This contract and this review do
   not authorize numerical/SQLite execution. This is a present task boundary,
   not a request for an optional approval flow. Continue only independently
   authorized preparation; production launch stays gated.

## Fixture and interface conditions

Case 1 is small and discriminating for custody: one native Jacobi track, one
requested interval, eight cells, one nonzero canonical directional field,
Some snapshot, saved native FrozenSpec v2 inside manifest v1, and two expected
constructor/accepted publications. The body must make the frozen density,
tolerances, source absence and step policy authoritative through the saved member,
rather than silently using normal preview defaults. Request, saved member and
recording must resolve to the same exact canonical bytes. Fixed-dt refusal remains
an expected failure boundary; it is not permission to tune dt or rerun on failure.

Case 2 is a separate material custody path, not a saved-material-rerun format.
Its stated Water/Air, fill, sample count, max-particle count, gravity, temperature
and memory values must be explicit in the inspected body. In particular, verify
that the selected constructor/fill with no emitter actually yields the stipulated
64 initial particles; do not infer that from `samples_per_axis` or cap alone, or
change the fixture after a failed run. If source preflight contradicts this
fixture, amend/review the contract before execution. One public material step may
perform up to 16 internal preparations under the existing backend retry policy;
do not describe it as one low-level evaluation or add an outer retry.

**Reviewed correction, resolved:** Case 2 now requires previews using actual
accepted state/time and preview/record time/dt association. Accepted dt can differ
from requested dt under the existing preparation policy. The future body must
assert generation, preview time, recorded time/dt and accepted controls consistently
against actual accepted state, without fabricating a literal accepted time or
requiring requested dt without a corresponding policy. Constructor time is zero.
No physics change was needed to correct the contract.

The test flag may bypass only the temporary force-validation gate. It must leave
snapshot freeze, supported-owner, immutable per-track intent, budget and run/step
binding validation intact. Do not call `Worker::start`, App update/start/rerun,
GUI, provider/model/child, emitter, collision mesh or observer paths. Keep exactly
one track and one requested interval per case. The owned scheduler/cancel/progress/
history arguments needed by `run_owned` must be explicit in the inspected helper
closure; no hidden test helper may launch another execution owner.

Desktop enables Rayon. Request threads=1 inside the production scoped pool means
**one owned Rayon pool worker**; the process also has its test/supervisor context.
This is not a no-parallel build, zero-worker execution or proof of a total OS
thread count. Preserve that wording in packet/results. Libtest threads=1 controls
test concurrency; selecting one fully qualified ignored exact name controls which
workload is requested. Neither substitutes for process/resource containment.

## Filesystem, teardown and outcome handling

Each case receives a different explicit absolute, fresh, exclusively owned root
created once by the existing supervisor. Helpers have no temp-directory/default
recording-directory fallback, do not replace the root, and create no paths outside
it. Verify path containment under the supervisor's protected-root policy. No Drop,
panic/success/failure cleanup, deletion or retry belongs in the body. Retain the
database, sidecars, manifests and failure evidence on every outcome.

The stated limits are requests for enforcement, not observed measurements: 30 s
wall, 20 s CPU, 1 GiB address space, 1 MiB per file, 8 MiB aggregate root, 1 MiB
captured output, then TERM/owned process-group KILL after 1 s. State whether a
bound or timeout fired; do not call a terminated run a failed scientific result
or infer peak resources from these limits. Stop after unexpected output,
selection, resource failure or timeout; preserve its disposition before any
further action. After termination, check owned descendants and inventory/hash
retained files before claiming immutable final evidence. Binary/source **seals**
can accompany the small root; do not imply that a large compiled executable must
fit inside the 8 MiB data budget.

## What passing cases can and cannot establish

A valid Case 1 result can establish one saved-native constructor-to-step dispatch,
matching force-bound header/publications, finalized member pin/hash/status and
cold-open association for this tiny request. Case 2 can establish corresponding
particle Request/record custody. Check exact metadata bytes after separate draft
mutation, progress/result count, publication count/order/generation, actual accepted
controls and recording status. Preserve integrity separately from acknowledged
recording completeness and any accepted-but-unrecorded tail on failure.

These cases do not validate force physics, legacy numerical equivalence, density
conversion, all pressure solvers, mixed saved members, frozen rerun, cancellation,
Worker admission/join, UI gestures or native presentation. Those remain distinct
bounded gates. Passing both is a review checkpoint, not automatic removal of the
temporary production gate. The workerless synthetic harness supplies none of
these runtime/archive claims.
